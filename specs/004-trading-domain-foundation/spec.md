# Feature Specification: RWA 交易能力底座

**Feature Branch**: `feat/004-trading-domain-foundation`

**Created**: 2026-09-03

**Status**: Ready for planning

**Input**: User description: "项目最终根据设计稿和接口开发；设计稿尚未提供，当前功能可大体参考
本地 RWA 交易原型，希望先完成除最终 UI 外的能力。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立可信账户会话 (Priority: P1)

作为已获授权的交易用户，我可以建立、恢复和结束账户会话，并获得与当前会话一致的账户、钱包和权限
状态，使未来界面能够安全地显示正确的身份与可用能力。

**Why this priority**: 身份和会话是读取受保护数据、管理钱包和发起任何交易操作的前提。

**Independent Test**: 使用有效、过期及无效凭证分别建立或恢复会话，验证只有有效会话获得账户状态，
失效会话不会保留受保护数据或允许后续操作。

**Acceptance Scenarios**:

1. **Given** 用户具有有效授权凭证，**When** 用户开始或恢复会话，**Then** 系统提供该用户的账户状态和
   可用交易钱包信息。
2. **Given** 凭证无效、过期或被拒绝，**When** 用户尝试建立会话，**Then** 系统拒绝会话且不泄露账户、
   资产或交易信息。
3. **Given** 用户已有有效会话，**When** 用户结束会话，**Then** 系统清除本地会话状态，且受保护操作要求
   重新授权。

---

### User Story 2 - 获取市场与资产全貌 (Priority: P1)

作为交易用户，我可以获取可交易标的、产品详情、市场状态、价格历史、收藏标的和自己的资产概览，
从而为后续交易决策提供一致且可追溯的数据。

**Why this priority**: 用户需要先理解可交易资产、价格和现有持仓，才可安全地做出交易决定。

**Independent Test**: 对有数据、空数据、分页数据和无权限数据分别请求市场及资产资料，验证返回内容
完整、归属正确，并保留精确数值和分页连续性。

**Acceptance Scenarios**:

1. **Given** 市场提供多个现货或合约产品，**When** 用户查询市场资料，**Then** 系统按产品类型返回
   可交易标的、行情、市场状态和价格历史。
2. **Given** 用户已有收藏或资产，**When** 用户查询个人市场与资产概览，**Then** 系统只返回属于该用户的
   收藏、账户、持仓和汇总信息。
3. **Given** 数据集需要分批取得，**When** 用户继续读取下一批数据，**Then** 系统提供连续且不重复的
   结果。

---

### User Story 3 - 安全地下达并跟踪交易 (Priority: P1)

作为交易用户，我可以先获得订单预览，再确认提交现货或合约订单，并持续了解订单、仓位及风险参数
的真实状态，而不会因网络重试而重复执行资金操作。

**Why this priority**: 下单及仓位管理涉及资产损失风险，必须在最终页面开发前先验证业务状态、精度和
失败处理。

**Independent Test**: 分别验证买入、卖出、做多、做空、价格变化、余额不足、重复提交、取消订单和
风险参数变更；每种结果都可从订单或仓位状态中重新取得并验证。

**Acceptance Scenarios**:

1. **Given** 用户提供完整且有效的交易意图，**When** 用户请求预览，**Then** 系统返回可供确认的估算
   结果、费用、资金需求和风险参数。
2. **Given** 用户确认有效预览，**When** 用户提交一次订单，**Then** 系统创建唯一订单并返回当前状态；
   重复提交不会创建第二笔经济上等价的订单。
3. **Given** 订单或仓位后续变化，**When** 用户查询或接收状态更新，**Then** 系统反映服务端
   当前状态，而不把待处理状态误报为成功。

---

### User Story 4 - 跟踪入金与提现 (Priority: P2)

作为交易用户，我可以查看钱包及可用资金，并跟踪入金和提现，使未来界面能够展示资金到达、处理中、
失败或需要人工处理的权威状态。

**Why this priority**: 入金和提现直接影响用户资产，需要在最终 UI 之前验证金额、网络和异步状态语义。

**Independent Test**: 对入金和提现的待处理、成功、失败、状态不明确和人工处理场景分别执行流程，验证
每笔记录的金额、币种、网络、状态和后续可执行操作保持一致。

**Acceptance Scenarios**:

1. **Given** 用户选择受支持的网络和资产，**When** 用户创建入金记录，**Then** 系统返回入金说明并允许
   后续查询到账状态。
2. **Given** 用户具有可提现余额和有效报价，**When** 用户发起提现，**Then** 系统创建唯一提现记录并
   允许后续查询结果。
3. **Given** 服务端表明入金后仍需资金划转，**When** 系统处理该状态，**Then** 系统明确标记需要后续能力，
   并返回非重试的 `funding_transfer_not_supported` capability state。

---

### User Story 5 - 保持账户状态及时且可恢复 (Priority: P2)

作为交易用户，我可以取得账户、订单、仓位和资金活动的最新状态；短暂断连或数据重同步不会导致
旧状态覆盖已确认结果。

**Why this priority**: 交易和资金操作会异步完成，可靠的状态更新是用户信任与正确界面呈现的基础。

**Independent Test**: 模拟连续事件、重复事件、乱序事件、断连、重连和要求全量重同步的事件，验证最终
业务状态与服务端查询结果一致。

**Acceptance Scenarios**:

1. **Given** 用户具有有效会话，**When** 订阅账户相关更新，**Then** 系统只接收该用户有权读取的更新。
2. **Given** 同一更新被重复接收，**When** 系统处理更新，**Then** 该更新最多改变一次业务状态。
3. **Given** 更新流中断或要求重同步，**When** 系统恢复连接，**Then** 系统恢复订阅并以权威状态消除
   缺失或过时数据。

### Edge Cases

- 会话在读取或提交操作期间失效时，系统拒绝未授权操作并将受保护状态转换为可恢复的失效状态。
- 金额、价格、数量、费用或保证金为零、缺失、超出允许精度或币种不匹配时，系统不创建经济操作，
  并提供明确的失败原因。
- 相同的命令在网络超时后重试时，系统保留原操作的可追踪结果，避免重复下单、创建入金记录或提现。
- 服务端暂不可用、返回部分列表、返回未知状态或连接中断时，系统保留最后确认状态并标明数据新鲜度，
  不将推测值视为最终结果。
- 提现授权被拒绝、超时，或入金链上状态异常时，系统保留可恢复状态并以服务端状态为准。
- 用户在一个账户中同时拥有现货资产和合约仓位时，系统保持产品、账户、币种和风险语义彼此分离。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许已授权用户创建、恢复和结束产品会话，并以当前授权状态保护后续操作。
- **FR-002**: 系统 MUST 提供当前用户的账户资料、设置、已登记设备和交易钱包状态。
- **FR-003**: 系统 MUST 仅向当前授权用户提供其账户、钱包、订单、持仓、资金与活动记录。
- **FR-004**: 系统 MUST 提供可交易股票、产品详情、市场统计、订单簿、市场时段和价格历史资料。
- **FR-005**: 系统 MUST 支持用户读取和更新自己的收藏标的，且不影响其他用户的收藏。
- **FR-006**: 系统 MUST 提供用户的组合汇总、账户余额、现货持仓及合约仓位，并保留每个金融数值的
  币种、单位与精度。
- **FR-007**: 系统 MUST 区分现货证券代币和永续合约产品，不混用其资产结果、保证金或风险属性。
- **FR-008**: 系统 MUST 在提交订单前提供订单预览，包括预计结果、费用、资金需求和风险参数。
- **FR-009**: 系统 MUST 支持不需要订单钱包签名的订单创建、读取和取消，并使订单状态可被后续查询。
- **FR-010**: 系统 MUST 确保每个金融命令可被安全地重试，不会因同一用户意图重复产生经济操作。
- **FR-011**: 系统 MUST 支持读取仓位、关闭仓位、更新或清除止盈止损，并在适用时更新杠杆设置。
- **FR-012**: 系统 MUST 将 `pending_signature` 订单表达为非重试的
  `order_signature_not_supported` capability state，并提供 `wait_for_feature` 后续动作。
- **FR-013**: 系统 MUST 提供入金资产与网络选择资料，并支持创建和跟踪入金记录。
- **FR-014**: 系统 MUST 将需要后续资金划转的入金表达为非重试的
  `funding_transfer_not_supported` capability state，并提供 `wait_for_feature` 后续动作。
- **FR-015**: 系统 MUST 在提现前提供可确认的提现报价，并支持创建、读取和跟踪提现记录。
- **FR-016**: 系统 MUST 提供可筛选的账户、资金和交易活动记录。
- **FR-017**: 系统 MUST 接收并处理与当前会话相关的账户、订单、仓位、入金和提现状态更新。
- **FR-018**: 系统 MUST 在更新重复、断连或要求重同步时恢复到可验证的权威状态。
- **FR-019**: 系统 MUST 将授权、权限、校验、限流、服务不可用及网络失败转化为稳定且可恢复的业务失败
  结果，不暴露敏感诊断内容。
- **FR-020**: 系统 MUST 以无损方式保存和传递金融数值，不进行未经定义的舍入或隐式单位转换。
- **FR-021**: 系统 MUST 记录或提供每个失败、待处理和成功命令的可追踪标识，以支持用户后续查询和
  问题排查。
- **FR-022**: 系统 MUST 在不依赖最终页面设计的前提下，向未来界面提供一致的业务状态、可用操作和
  恢复指导。
- **FR-023**: 系统 MUST 只在受控演示或 Mock 环境验证订单、入金和提现命令。该环境 MUST 与
  生产账户、生产钱包和真实资产隔离，任何验收操作均不得产生真实资产后果。

### Out of Scope

- 最终页面、视觉、文案、导航和响应式实现。
- 订单 wallet action 的创建、签署或提交，包括 `completeOrderWalletAction`。
- 资金准备计划、账户间划转和 Claim 的 domain model、repository、Provider、命令及业务测试。
- 对 `openapi/main.yaml` 或生成客户端的修改。

### Key Entities

- **产品会话**: 用户的有效授权上下文，关联账户、权限、钱包及可读取或执行的业务操作。
- **市场产品**: 可交易标的在现货或合约市场中的具体交易规则、行情、价格历史和风险属性。
- **组合与账户**: 用户资产汇总、各账户余额、现货持仓和合约仓位的权威快照。
- **订单预览**: 在提交前说明交易意图的预计成交、费用、资金需求和风险参数。
- **订单**: 已提交交易意图的可追踪记录，包含唯一性、防重复语义及随时间变化的状态。
- **仓位**: 由成交产生的现货资产或合约风险敞口，包含可调整的止盈止损或杠杆条件。
- **钱包与授权**: 用户可用交易钱包及提现等范围内操作的授权状态。
- **资金操作**: 本阶段仅包含入金和提现的独立可追踪记录及其资产、网络、金额和状态。
- **活动记录**: 账户、交易和资金相关的按时间排序事件，支持用户核对发生过的操作。
- **实时更新**: 使本地业务状态与权威账户、订单、仓位和资金状态保持一致的状态变更通知。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对本规格覆盖的每项读取和命令，100% 的成功、拒绝、待处理和失败验收场景均可在不依赖
  最终 UI 的情况下验证。
- **SC-002**: 在重复提交、网络超时重试和重复状态更新的测试中，100% 的金融命令最多产生一次经济结果。
- **SC-003**: 对至少 50 个包含现货、合约、入金、提现和会话状态的代表性场景，100% 的金额、币种、单位和
  状态与权威记录一致。
- **SC-004**: 在断连和恢复的代表性测试中，100% 的账户、订单、仓位和资金状态可在恢复后重新取得，
  且不会将待处理或失败结果呈现为成功。
- **SC-005**: 在权限、校验、限流和服务异常的代表性测试中，100% 的失败结果提供可执行的恢复方向，
  且不包含凭证、完整金融载荷或内部堆栈信息。

## Assumptions

- 最终 UI 的视觉、信息层级、导航、文案和响应式行为不属于本功能的交付范围；当前原型仅用于识别
  候选业务流程，不是最终验收标准。
- 已有接口契约定义了本功能可使用的业务能力；未在契约中定义的字段、状态或操作不纳入范围。
- 现货证券代币与永续合约均以 USDC 计价，但其资产结果、保证金和风险规则彼此独立。
- 认证提供方负责用户身份凭证；本功能负责按已获授权的会话使用该凭证，而不保存或展示敏感凭证。
- 未来设计稿可能改变页面组成和交互顺序，但不得改变本规格已经验收的资金、订单、权限和状态语义，
  除非通过新的规格变更明确批准。
- 本阶段使用受控演示或 Mock 环境验收命令；测试账户、钱包和资产与生产环境隔离，不允许产生真实
  价值转移。具体采用哪一种受控环境可在实施计划中依据可用测试基础设施确定。
- `pending_signature` 订单和需要后续划转的入金分别映射为稳定 capability state；它们不是失败，不可
  重试，也不提供当前范围内的执行命令。
