# HIP3 deterministic gaps — frontend evidence

## D03 ordering addendum

The Favorites ranking exposes **Reorder favorites**. Its editor independently
loads every page with no product-kind/search filter before enabling Save. It
uses the service's order and submits an exact permutation; the visible filtered
page is never treated as the full collection. The bStocks Favorites ranking also
uses server-filtered pagination/order rather than locally filtering the general
market list.

Reads are bounded to the server's 1,000-favorite maximum and 1,000 requests (the
worst case of one record per page; empty advancing pages are bounded too). A
partial-read error enables explicit reload, not automatic unbounded retries.
An ambiguous save or HTTP 409 triggers one complete reload and requires another
user confirmation. Neither case automatically replaces the previous collection.
Build/save generation tokens protect both account switches and same-account
reloads from obsolete responses overwriting the editing baseline.

Targeted evidence: `/private/tmp/hip3-favorite-reorder-final.log` — 22 tests
passed, including the two entry/editor UI cases and eight editor-provider cases.
These changes postdate the earlier root full-suite baseline below and therefore
still require root's final integrated quality run.

This is implementation evidence for the current HIP3 goal, not a claim that all
HIP3 features, mainnet execution, or live trading acceptance are complete.
OpenAPI/SDK is pinned to contract commit
`51596553ba9b1ca29e2ff1f231c9a4ad3b0207e1`, generated by the repository scripts.
No generated SDK files were hand-edited.

## Important behavior and boundaries

- Favorite commands return the result of that request (`Future<bool>`), not the
  mutable global status of a different account's command. The screen no longer
  keeps a permanent local favorite override. It consumes refreshed server data.
- Failed favorite submissions trigger reconciliation because a lost response
  does not prove that the server failed to persist the update. The UI still does
  not announce success for such a request.
- Market list polling re-reads the loaded page window from its first page and
  publishes it atomically. It never appends a fresh first page to old cursors.
  Poll failures retain earlier results with an error. Network reads are not
  signatures or broadcasts.
- The quote component owns at most one expiry timer. It does not own a repository
  or make HTTP calls. It cancels on background/offstage/dispose and checks wall
  time on return. It is a presentation component: execution-time validation is
  still the responsibility of the existing preview/action path and D01 binding.
- Missing validity or observation time is unverified, not fresh. Mark and HIP3
  Oracle are explicitly distinguished from US stock-market reference prices.
- Holdings coverage is computed by the server before pagination. Repeated page
  counts are not added. It is a HIP3 display scope, not a full-wallet guarantee.
  Unmapped positions make the status unreliable even if another field says
  complete. `HoldingStock.referencePrice` is nullable; the portfolio mapper does
  not use it to invent valuations or turn mark/entry price into a reference price.
- Activity `business_type` null remains absent for non-HIP3 records; explicit or
  forward-compatible unknown is shown as unclassified. The client does not infer
  opening/closing from long/short, and does not turn cumulative funding into
  funding settlement events.
- English and Chinese copy is generated from ARB source. The list keeps its price
  row layout; wrapping/minimum height accommodates large text rather than clipping.
